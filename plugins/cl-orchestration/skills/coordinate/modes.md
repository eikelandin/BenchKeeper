# Worker modes

How a worker runs in each mode, and the bounds of each. Orca starts the workers by [orca.md](orca.md), which links here where a step needs a mode's rule.

## Modes

Each project's `mode` comes from its policy ([policy.md](policy.md)). A leading `--mode supervised` run argument lowers every project of the run to supervised; nothing raises a mode. The handoff's `Mode:` line holds each project's mode for the run and, where lower than its policy's, why; a resumed run keeps it.

- **Supervised:** a Claude Code worker starts in auto mode (`--permission-mode auto`, Manual where auto mode is unavailable) in a terminal the coordinator makes, with the rule file of [Worker rules](#worker-rules); another agent's worker starts through Orca's own launch, so its prompts depend on Orca's agent permission setting, the user's choice ([orca.md](orca.md#start-the-run)). The coordinator writes no flag that bypasses or skips permission prompts; a worker's prompts are the owner's ([A permission dialog](orca.md#a-permission-dialog)). Every question to the owner blocks its own item until answered; other items go on.
- **Automatic:** a Claude Code worker starts only with the sandbox on (below), with `--permission-mode dontAsk` and `--settings <run folder>/settings/<id>.json` on its launch, the absolute path that the `--check` read of [Automatic start](#automatic-start) took; a call the bounds and allow rules do not cover is denied, never prompted. No flag that bypasses permission prompts, in any form, and its settings file sets `disableBypassPermissionsMode` to `"disable"` ([settings](https://code.claude.com/docs/en/settings)), so a hook cannot switch the session to bypass mode either ([changelog](https://code.claude.com/docs/en/changelog)). The coordinator takes the recommended default only for a safe, reversible choice and records it in the handoff's `## Decisions` and the report. A worker takes one issue, whatever `issuesPerWorker` says: it cannot commit, so it cannot switch branches. It is released at its report, and each follow-up of it is a new start ([Sandbox on](#sandbox-on)). Its spec changes as [spec-template.md](spec-template.md#automatic-mode) says.

`dontAsk` only refuses tool calls that no allow rule lists; it decides no question: an owner-only decision is a gate ([Gates](#gates)).

### Gates

A gate holds one item for the owner while the other items go on ([Owner-only decisions](SKILL.md#owner-only-decisions)): in supervised mode every question put to the owner, in automatic mode an owner-only decision only.

- Worker side: the worker never decides an owner-only question and never takes a default for it, also where a tool call would pass. With a question command and in supervised mode it asks and waits for the answer; otherwise it stops that item and reports BLOCKED with the question ([spec-template.md](spec-template.md)).
- Coordinator side: put each such question to the owner once, in your own words, as an approval whose What starts with `question` and names the issue and the decision ([approvals.md](approvals.md)), and record it in `## Open` with the worker (its id and, where it asked, the question's id) in place of the head. A BLOCKED report keeps its worktree and branch ([Outcomes](SKILL.md#outcomes)), and its item task gets an Orca gate once its worker settled ([Tasks and gates](orca.md#tasks-and-gates)).
- After the answer the Gates section of [orca.md](orca.md#gates) brings it to the same worker, a supervised Claude Code worker gets it by a follow-up `send` in place, or by a new start when it is released, its terminal is gone or its terminal shows no auto mode, and a `follow_up` not confirmed in its own terminal is kept for the owner, with nothing stopped or started ([orca.md](orca.md#start-the-run)); an automatic worker's answer, and one whose worker failed, was stopped or is gone, goes to a new start in its worktree with the gate form of the spec's Branch line ([spec-template.md](spec-template.md), [SKILL.md](SKILL.md#loop), step 3) and the answer under `Shared context:` as a line of its own marked `(owner)` ([Owner-only decisions](SKILL.md#owner-only-decisions)). Either counts like a follow-up for the caps ([SKILL.md](SKILL.md#loop), step 5). The item goes on and ends with a new report. An answer that holds, and no answer, keep it blocked: list it in the report.

### Worker rules

[worker-rules.json](worker-rules.json) is one deny list for each Claude Code worker that runs in a session of its own. Deny wins over ask and allow, across every settings scope, so a broad allow rule in the user settings does not lift it ([permissions](https://code.claude.com/docs/en/permissions#manage-permissions)). It acts in every mode, auto mode included ([permission modes](https://code.claude.com/docs/en/permission-modes#actions-no-mode-auto-approves)). Orca's own launch starts no Claude Code worker ([orca.md](orca.md#start-the-run)). The file holds deny rules only: deny rules hold in every mode, and on entering auto mode Claude Code drops broad allow rules (`Bash(*)`, wildcarded interpreters, package-manager run commands, `Agent` and `Monitor` allow rules) while narrow ones stay in effect ([permission modes](https://code.claude.com/docs/en/permission-modes)). Without managed settings, a `managed-mcp.json` or a Team or Enterprise login, a mod can approve a call a deny rule refuses, and a PreToolUse hook can approve what `dontAsk` would deny. Mods that Claude writes do not load in `dontAsk` mode, and a mod's own tool calls raise no prompt under an ask rule or in `dontAsk`, so the Edit rules that go in as ask do not bind them; deny rules still do ([changelog](https://code.claude.com/docs/en/changelog)).

| Deny rules | Supervised | Automatic |
| --- | --- | --- |
| `gh pr merge`, `gh release`, `gh repo create`, `delete` and `edit`; `git push` with `--force`, `-f`, a `+` refspec, `--delete`, `-d`, a `:` refspec, `--mirror` or `--prune`; reading `.env`, `.env.*` and `secrets/` | refused; the read rules bind the file tools, the Bash file commands Claude Code recognizes (such as `cat` and `head`) and Bash redirections ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit)), and any other Bash command still reads those files (`cut -d= -f1 .env` did) | refused |
| `git push`, `gh pr create`, `gh pr comment`, `gh issue` writes, `rm -r` (`-R`, `-fr`, `--recursive`), `WebFetch` | refused: push, pull request and issue comments stay with the coordinator ([Commit and push](#commit-and-push)) | refused |
| edits under `.claude/`, `.github/` and any `.git` | refused to the file tools | refused to the file tools (`dontAsk`) |

- Supervised (Orca): before each start and follow-up of a Claude Code worker, `node <skill folder>/worker-settings.mjs --supervised <worktree path> <project path>` writes the list as `<worktree path>/.claude/settings.local.json`, then the same command with `--check` before `--supervised` must exit 0. Claude Code reads that file in the folder it starts in beside the main checkout's and applies the permission rules of both ([settings](https://code.claude.com/docs/en/settings#where-claude-code-keeps-the-local-file-in-a-git-repository)). The file also sets `permissions.disableBypassPermissionsMode` to `"disable"`, which keeps anyone from entering bypass mode: Claude Code then rejects `--dangerously-skip-permissions` and ignores an agent definition's `permissionMode: bypassPermissions` ([settings reference](https://code.claude.com/docs/en/settings-reference)). It closes what the launch's `--permission-mode auto` does not: bypass in the Shift+Tab cycle, which a `defaultMode` of `"bypassPermissions"` in the user, `--settings` or managed settings puts there, and a session resumed in a settings file's mode ([orca.md](orca.md#start-the-run)). Where the main checkout's file sets the same key, its value applies (unverified: that the key takes effect from the worktree's file). The write refuses a rule file with any other content, a file without the key included, and the item is BLOCKED. Deny rules need no workspace trust. A rule path that starts with `/` counts from the worktree, so the file names no host path. The script refuses a path that is no linked worktree of that project ([Sandbox on](#sandbox-on)), never overwrites another file there and never writes or reads through a link: any failure starts no worker and makes the item BLOCKED. It also lists `/.claude/settings.local.json` in the shared `.git`'s `info/exclude`, which git reads for every worktree and the main checkout, and `--check` fails without that line: `git add -A` leaves the file out, `git add -f` does not, and the spec forbids staging it ([orca.md](orca.md#start-the-run)).
- Supervised, such a worker commits and reports, and the coordinator pushes its branch and opens its draft pull request ([Commit and push](#commit-and-push)); its spec changes as [spec-template.md](spec-template.md#supervised-claude-code-worker-on-orca) says. Its file tools are refused under `.claude/`, `.github/` and any `.git`. With the sandbox on in a settings file the worker loads (the user settings, the main checkout's `.claude/settings.local.json`), the sandbox takes those Edit denies for Bash too and closes the same paths to git ([sandboxing](https://code.claude.com/docs/en/sandboxing#permission-rules)): the worker's commit can fail, and it then reports BLOCKED.
- Automatic: `worker-settings.mjs` adds the list to the settings file ([Sandbox on](#sandbox-on)), minus a rule that the template's deny list already matches (`Bash(gh *)`, `Bash(git push *)`, `WebFetch`, `.claude`). An Edit rule goes in as ask, which `dontAsk` refuses: the sandbox closes a deny rule's paths to Bash too, and so would close the shared `.git` to git. A mod's own tool calls pass those ask rules ([Worker rules](#worker-rules)): against them, the `.github/` check of [Commit and push](#commit-and-push) (step 2) and its read of `<W>/.git` hold.
- A Bash rule matches the command as written: `git -C . push`, `gh api` and `/bin/rm` pass it ([permissions](https://code.claude.com/docs/en/permissions#bash-rule-limits)). A `WebFetch` rule names hosts to match, never hosts to leave out, and deny wins over allow, so the deny refuses every host, also one an allow rule lists. In auto mode a supervised worker's Bash write to its rule file goes to the classifier, and the deny rules do not bind Bash writes. A `Read` deny also refuses Edit and Write on that path, `.env.example` included, at any depth, and in automatic mode the sandbox closes it to Bash too ([Read and Edit](https://code.claude.com/docs/en/permissions#read-and-edit), [sandboxing](https://code.claude.com/docs/en/sandboxing#permission-rules)).

### Sandbox on

The worker's settings file is written by `node <skill folder>/worker-settings.mjs <worktree path> <project path> <run folder>/settings/<id>.json <domain>...`, the paths absolute, the domains being the policy's `sandbox.allowedDomains`, never by hand: [automatic-settings.json](automatic-settings.json) with `//W/` as the worktree, `//C/` as the real path of `<project path>/.git` and the domains as `sandbox.network.allowedDomains`. The folder the worktree's `.git` file names, resolved as git opens it (each link followed before a `..` applies), must lie directly under `<project path>/.git/worktrees`, compared by file identity, so no other spelling of a folder and no folder outside the project's `worktrees` folder passes. The worktree's `.git` file goes into `sandbox.filesystem.denyWrite`: on macOS the sandbox runtime alone blocks only creating, removing and renaming it, not a write in place. The worker cannot write the file: the file tools, the sandbox and `dontAsk` keep it to its worktree.

- Claude Code v2.1.323 or later (`'<claude path>' --version`, the executable every launch line starts), the CedarLoom minimum, also for a supervised Claude Code worker ([orca.md](orca.md#start-the-run)): an older version may ignore a key it does not know, and may start a session that asks for auto mode in a mode that allows more.
- The file tools keep to the worktree (`blockWritesOutsideWorkingDirectories`, `blockReadsOutsideWorkingDirectories`), and with the sandbox on the read block also closes the home folder and the other users' folders to Bash. Bash writes reach the worktree minus its `.git` file, the temporary folder and the shared `.git` minus `hooks`, `config` and the paths of the deny rules below, so a package manager whose cache lies in the home folder fails there (`npm ci`: `EPERM` on `~/.npm/_cacache`). The credential entries keep SSH, cloud, container and GPG credentials closed and unset the GitHub and npm tokens for every command.
- The worker reaches no Orca app: the read block closes the home folder, where Orca's runtime file lies, and the sandbox closes local sockets ([sandbox runtime README](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/README.md): "Unix sockets are **blocked by default** on both platforms", on Linux through seccomp on x64 and arm64 only), and neither is opened. The credential entries also unset `ORCA_PAIRING_CODE`, `ORCA_REMOTE_PAIRING` (the Orca CLI reads a pairing code from either) and `ORCA_AGENT_SESSION_SPAWN_TOKEN`. Probe step 5 of [Automatic start](#automatic-start) checks the bound on the host. So it runs no Orca command and ends with its report as its final answer, which the coordinator reads through Orca ([Worker reports](orca.md#worker-reports)); it never asks.
- The network allow list is `strictAllowlist` with the policy's hosts: what the project's own tools fetch. The worker neither pushes nor runs `gh`, so no GitHub host is needed for git. The `Bash(git push *)` deny stops the plain form only: `git -C . push` passed it and failed at the sandbox's network proxy, so the push bound rests on the allow list and on credentials, and a GitHub host in the allow list runs the project supervised ([Automatic start](#automatic-start), check 4). A known residual risk: the sandbox's proxy does not inspect TLS, so code in the sandbox can reach other hosts through an allowed one ([security limitations](https://code.claude.com/docs/en/sandboxing#security-limitations)). On macOS the credential entries cover files and environment variables, not the Keychain: the sandbox profile allows the security daemon ([sandbox runtime source](https://github.com/anthropic-experimental/sandbox-runtime/blob/main/src/sandbox/macos-sandbox-utils.ts)), so a sandboxed command may read a Keychain item, such as the Claude Code credentials item.
- The deny rules close the paths that configure Claude Code or run later outside the sandbox (`.claude`, `.mcp.json`, `.vscode`, `.idea`, `.bashrc`, `.zshrc`, `.gitconfig`, `.envrc`, `.npmrc`, `.husky`), and `commondir` and `config.worktree` in the shared `.git` and in each of its `worktrees/*` folders, which would make git load configuration the worker wrote: in the main checkout and in any worktree of the project, outside the sandbox. An item that must change one is BLOCKED for the owner.
- For each folder under the shared `.git`'s `worktrees` when the file is written, the script adds the two rules with that folder's name beside the `worktrees/*` pattern rules. Only a rule that names a path keeps its folder from being renamed, and so from being swapped for a copy with another `commondir` (on Linux through mount points: the sandbox makes each folder between a named path and the write root one, which the kernel refuses to rename), and on Linux the sandbox skips a pattern rule for writes. A folder made after the file was written has the pattern rules alone, until that worker's next settings file: on macOS they close its two files but not a rename of the folder, on Linux nothing. So no worktree of a project is made while an automatic worker of that project is started and not yet released:
  - An automatic worker is released as soon as its report arrives. Its staged change waits in the worktree, which stays, for [Commit and push](#commit-and-push) to open its pull request. It counts as released only once its session has ended, which [Clean up](orca.md#clean-up) confirms.
  - Every later turn of that worker (a follow-up with review findings, a re-check, a conflict with the default branch) is a new start in the same worktree, with its settings file written again, so that file names the folders that exist then.
  - This is the regular case, also with one worker per project: the next issue of the project gets its worktree only once the worker before it is released, and a follow-up never runs under a settings file older than a worktree.
  - Workers that start together get their worktrees before the first of their settings files. A worktree needed while one of them still works waits until that worker is released.
  - Some automatic workers are never released or not released yet: a worker whose terminal a person typed in is never released, a start held at a dialog has loaded its settings file and so counts as started, and a worker whose session end [Clean up](orca.md#clean-up) cannot confirm stays unreleased. While one of these lasts, no worktree is made in its project, and the project's waiting issues are listed for the owner in the report and do not hold the run open.
  - A supervised Claude Code or Codex worker stays open for follow-ups, as [Start the run](orca.md#start-the-run) says.

  The `commondir` read of [Commit and push](#commit-and-push) is the second check: the sandbox's part of this is not tested.
- Lists of rules and folders merge across every settings scope the worker loads, so the bounds are the template and the [Worker rules](#worker-rules) plus the user's and the main checkout's entries.

### Automatic start

Check 2 runs before every start of an automatic worker (its first start, a retry, each follow-up, the probe), the others before the first automatic worker of each project in a run, in this order. A failure, except the `--check` read of check 2, runs that project supervised for the rest of the run where [orca.md](orca.md#fallback-to-supervised) offers that fallback, else starts nothing there; write it in the handoff's `Mode:` line and name the check or step in the report. A supervised worker has none of the automatic bounds: the report says so for that project, and with Orca names what its workers run under ([orca.md](orca.md#fallback-to-supervised)).

1. `'<claude path>' --version` is v2.1.323 or later; after a failure the fallback starts no Claude Code worker either ([orca.md](orca.md#start-the-run)).
2. `worker-settings.mjs` wrote the worker's settings file right before the start ([Sandbox on](#sandbox-on)) and exited 0. A hand-made file can keep a placeholder or a wrong path and still load, with its deny rules pointing nowhere. Then, as the last command before Orca starts the worker's session, `node <skill folder>/worker-settings.mjs --check` with the same arguments exits 0: it reads the file as it is then and passes only the exact text the script writes for that worktree, that project and those domains. Claude Code starts with an empty settings file as with none, so without the sandbox and the file-tool bounds. Any other exit starts no worker: it makes the item BLOCKED, and for the probe it fails check 5.
3. No hook of the user settings, of managed settings, of an enabled plugin, of the project's `.claude/settings.json` or of the main checkout's `.claude/settings.local.json`, no MCP server of the user settings, of an enabled plugin or of the project's `.mcp.json`, no monitor or LSP server of an enabled plugin, no status line command, `apiKeyHelper`, `otelHeadersHelper`, `awsAuthRefresh`, `gcpAuthRefresh`, `awsCredentialExport` or `fileSuggestion` command of those settings files and no process an enabled mod starts runs a file inside the repository or a tool that loads the repository's code or configuration (a formatter, a linter, a package script): these run outside the sandbox, so a worker that edits such a file gets its code run unsandboxed.
4. No entry that defeats a bound, in managed settings, the user settings, the project's `.claude/settings.json` or the main checkout's `.claude/settings.local.json`: a `sandbox.excludedCommands` entry (an excluded command runs outside the sandbox, and an allow rule lets it run without a prompt), a `sandbox.network.allowUnixSockets` or `allowAllUnixSockets` entry (the SSH agent, a container socket), an `allowRead`, `allowWrite` or `additionalDirectories` entry outside the worktree, a `true` for `sandbox.allowAppleEvents` (a command then runs unsandboxed and can script running apps), `allowNestedUserNamespaces`, `enableWeakerNestedSandbox`, `enableWeakerNetworkIsolation`, `network.allowLocalBinding` or `filesystem.disabled` (the template pins each to `false`; whether that wins over the user settings is not tested), a `sandbox.network.allowMachLookup`, `network.httpProxyPort` or `network.socksProxyPort` entry, a `sandbox.enabledPlatforms` entry that leaves out the host's platform, a `sandbox.ripgrep`, `sandbox.bwrapPath` or `sandbox.socatPath` override, and no GitHub host (`github.com`, a subdomain of it, `*.githubusercontent.com`) in the merged network allow list or in a `WebFetch(domain:...)` allow rule of those files (such a rule may add its host to the sandbox's allow list). Name in the run report the other allow rules and `sandbox.network.allowedDomains` entries of those files.
5. The probe: one worker with the same launch in a scratch worktree of the project (create `.husky/` there first, and a second scratch worktree of the project beside it before the probe's settings file is written, so that the file names its folder), its spec these steps. Check each result yourself where you can.
   1. Version: as check 1.
   2. The Write and Read tools on a new file in the run folder are refused, and no file appears there. The Write refusal names `blockWritesOutsideWorkingDirectories`, which shows the settings file loaded.
   3. Bash `touch` and `cat` on a file you wrote in the run folder before the probe (its absolute path, filled in) fail with `Operation not permitted`. The file must exist: on macOS the sandbox answers a path that does not exist with `No such file or directory`. On Linux the sandbox mounts an empty tmpfs over a read-denied folder, so there the criterion is that both commands ran on that path (a refusal by a permission rule or a hook fails this step), that `cat` prints none of the file's content, that the worker reports both outputs verbatim, and that you, as the coordinator, then find the file on the host with its content and modification time unchanged.
   4. The Write tool and Bash `touch` on `.claude/settings.json`, `.mcp.json`, `.husky/pre-commit`, `.envrc`, `.npmrc` and `.git` are refused, and Bash `touch` on `<common .git>/hooks/probe`, `<common .git>/config`, `<common .git>/commondir`, `<common .git>/config.worktree`, and `commondir` and `config.worktree` in `<common .git>/worktrees/<id>/` and in the second scratch worktree's folder there (the absolute paths, filled in) fails with `Operation not permitted`. Bash `mv` of the second worktree's folder there to `<its name>.moved` fails and the folder keeps its name. On macOS the message is `Operation not permitted`. On Linux the criterion is the kept name: the folder is a mount point there ([Sandbox on](#sandbox-on)), so the message may be `Device or resource busy` (`EBUSY`). A touch or the `mv` that passes there shows that the sandbox does not take the rules that name that folder. In the worktree, Bash `printf '' >> .git` exits non-zero with `.git` keeping its content (the shell words the message: zsh `operation not permitted: .git`, bash `.git: Operation not permitted`; on Linux `Read-only file system`; the message may differ), and `mv .git .git.moved` fails with `.git` keeping its name: the template's `sandbox.filesystem.denyWrite` entry closes the file, and the rename also by the sandbox runtime's own rules, on macOS through its move-blocking rules, on Linux through its write deny on a `.git` file.
   5. Bash `<Orca CLI> orchestration run-list --json`, the Orca CLI by its absolute path (on macOS `/Applications/Orca.app/Contents/Resources/bin/orca`, on Linux the path it is installed at), fails with `runtime_unavailable` or `runtime_access_denied`. Any other result, also a command that is not found, fails this step: it tests the bound of [Sandbox on](#sandbox-on) that keeps the worker from every Orca app.
   6. Bash `curl -sS -I https://example.com` is refused.
   7. Bash `claude -p 'reply ok'` fails, and its output shows a sandbox cause: `Operation not permitted` on a path in the home folder (the program or its configuration; zsh and Node.js word it `operation not permitted`), or a connection the sandbox's proxy refused. The worker reports that output verbatim. A reply, a timeout and any other failure (an expired login, a usage limit, another API error, a refusal by a permission rule or a hook, `command not found`) fail this step, since none shows the sandbox stopped the session. On Linux the tmpfs of step 3 hides the home folder, so the step passes there only on the proxy's refusal, and `command not found` for a program in the home folder fails it. The launch already unsets `CEDARLOOM_ROLE`, and the role guard refuses a command that names it before it runs, so the step leaves the variable out.
   8. A write in the worktree and `git add` succeed; `git push origin HEAD:refs/heads/probe/<r>` is refused, `git -C <W> push origin HEAD:refs/heads/probe/<r>` (a form the deny rule does not match) fails at the network: for an HTTPS origin with `CONNECT tunnel failed, response 403` from the sandbox's proxy, for an SSH origin at its connection (the message may differ). A permission refusal of that call fails this step, since it tests no network bound. Then, as the coordinator, `gitW ls-remote origin refs/heads/probe/<r>` ([Commit and push](#commit-and-push)) prints nothing; commit on the host as [Commit and push](#commit-and-push) says, and run its push with `--dry-run`.

Pass rule: every step as stated, and the probe's report arrives as its final answer, read through Orca as [Worker reports](orca.md#worker-reports) says; no report within `stallMinutes` fails it. Steps 2 and 6 also pass on `dontAsk` alone; without the sandbox, step 3 names don't-ask mode instead of `Operation not permitted` and step 8's `git add` is refused. After the probe, first and without git, remove each file that a passing touch of step 4 made in the shared `.git` (an empty `commondir` there stops every git command in the project) and give a folder or `.git` file that a passing `mv` renamed its name back. Then remove both scratch worktrees, each as an automatic worker's: the `commondir` read of [Commit and push](#commit-and-push) on its folder, then `git --no-replace-objects -C <project path> -c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.ext.allow=never worktree remove <worktree path>`. `worktree remove` refuses a worktree with changes, untracked or staged: the probe's file when the probe ended before step 8's commit, a file a passing touch of step 4 made in the worktree. For the probe's worktree only, and once you have read those files, add `--force` after `worktree remove`. The second scratch worktree and every worker's worktree are removed without it. Then delete the branch `probe/<r>`: its commit is the probe's, never pushed.

### Commit and push

The worker stages its change and reports the branch, the staged files and a commit message. The worker can write the refs, replace objects and grafts of the shared `.git`, so these steps take commits from origin, never from local refs or history. It can also write the worktree's folder there, which `<W>/.git` names: before each step and any other git command of yours in `<W>` (Clean up's too), read `<W>/.git` and that folder's `commondir` with the file tool. The folder lies directly under `<project path>/.git/worktrees/`, `commondir` holds `../..`, the folder's `config.worktree` is missing or empty, and the shared `.git` has no `commondir`; anything else (git would load configuration, and so commands, the worker wrote) makes the item BLOCKED. An empty `config.worktree` is accepted: while another automatic worker of the project runs a command, the Linux sandbox binds an empty file over each deny path that does not exist, and removes it after the command. The settings file's deny rules keep these closed to the worker; this read is the second check.

Every git command of yours in `<W>`, below and in Clean up, runs as `git --no-replace-objects -C <W> -c core.hooksPath=/dev/null -c core.fsmonitor=false -c protocol.ext.allow=never`, written `gitW` here: a hook (also of a fetch, which writes a ref), a monitor or an `ext::` remote would run worktree code outside the sandbox, so the project's hooks do not run here and its CI checks the change. `policy.mjs` pins the same three.

1. `gitW rev-parse HEAD` is a commit of origin: `gh api repos/<owner/repo>/compare/<that sha>...<branch>` (while origin has no such branch, `<default branch>`) gives `identical` or `ahead`. In a merge round (step 5), `gitW rev-parse MERGE_HEAD` is the sha that step merged. Anything else (a worker commit) makes the item BLOCKED.
2. `gitW diff --cached --no-renames --name-only` (in a merge round, against `MERGE_HEAD`) lists the reported files, all in the owned paths. A path under `.github/` is the owner's (workflows, the actions and scripts they call run in CI with the repository's secrets before review): BLOCKED with the question, before the push. The project's own tests and scripts, which CI runs too, are outside this check.
3. Write the message to a file in the run folder with the file tool, then `gitW commit -F <file>`. The commit is signed where the owner's git configuration signs. Before the push, check the commit itself: `git commit` takes its tree from the index's cache and adds a `MERGE_HEAD` file as a parent, both of which the worker can write, so steps 1 and 2 do not prove what it holds.
   Right after the commit, `gitW rev-parse HEAD` once gives `<commit sha>`; the checks and the push take that sha and never resolve `HEAD` again, since the worker can move the ref in between.
   - `gitW cat-file commit <commit sha>` has exactly one `parent` line, the step 1 sha (in a merge round two: that sha, then the merged sha). Read the raw commit, never `rev-list` or `log`: a grafts file the worker wrote changes the parents they show.
   - `gitW diff --no-renames --name-only <step 1 sha> <commit sha>` (in a merge round, against the merged sha) prints the list step 2 accepted.

   Anything else makes the item BLOCKED, and nothing is pushed. Then `gitW push origin <commit sha>:refs/heads/<branch>`. First round: `gh pr create -R <owner/repo> --draft --base <default branch> --head <branch> --title "<your own words>" --body-file <file>`, the file holding the commit message and, where the policy's `closeIssue` is true and the pull request is not one of an approved pull request list, a line `Closes #<number>` for its issue ([Ready](review-and-merge.md#ready)). A new title or body the worker answers with is the coordinator's to set, a new body with the same `Closes` line.
4. Before a follow-up, `gitW fetch origin <branch>` and `gitW merge --ff-only <sha>`, the sha `gitW ls-remote origin refs/heads/<branch>` prints: `gh pr update-branch` moves the branch on origin.
5. A conflict with the default branch: the same with `<default branch>` and `merge --no-commit` in place of `--ff-only`, then the follow-up. The worker resolves and stages, and step 3's commit is the merge.

A supervised Claude Code worker on Orca commits on its branch, fetches and merges itself, and reports its branch, its head commit, a proposed pull request title and a body ([spec-template.md](spec-template.md#supervised-claude-code-worker-on-orca)), so steps 1, 3's commit, 4 and 5 do not apply. The `commondir` read and `gitW` above do. Such a worker runs under the host login without the automatic bounds and can write the shared `.git`, its config included: these steps catch a mistake, not a worker that works against them. The push runs hook-free as well: a hook in that `.git` is the worker's to write, so it would run the worker's code as you; the worker's own commit ran the project's commit hooks, and CI checks the change. `gitW rev-parse refs/heads/<branch>` prints the reported commit, which is `<commit sha>` from then on, and after `gitW fetch origin <default branch>`, every path that `gitW diff --no-renames --name-only refs/remotes/origin/<default branch>...<commit sha>` or `gitW log --format= --name-only --no-renames refs/remotes/origin/<default branch>..<commit sha>` lists is owned, by step 2's rule: the push publishes every commit, so a file one commit adds and a later one removes counts too, and the diff covers a merge, for which the log lists no files. Anything else makes the item BLOCKED, and nothing is pushed. Then push and open the draft pull request as the end of step 3 says: the title in your own words, which may follow the one the worker proposed, and the worker's body written to a file in the run folder with the file tool for `--body-file`, never on the command line. A new title or body for a follow-up goes the same way through `gh pr edit <n> -R <owner/repo> --title "<your own words>" --body-file <file>`. A follow-up's new head is pushed the same way; origin refusing it as no fast-forward makes the item BLOCKED, never a forced push. A batch's worker goes on in the same worktree meanwhile: a git command that fails on a locked ref runs again at the next wake-up, and a second failure makes the item BLOCKED.
